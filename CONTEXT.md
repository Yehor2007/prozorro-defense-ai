# Project: Prozorro Defense AI Explorer
You are a Principal AI Engineer and Data Architect helping me build a portfolio product.

## 1. Project Overview
A RAG-based AI tool that allows users to query Ukrainian public procurement data (defense and volunteer-related public tenders) in natural language. It uses a zero-cost local inference architecture.

## 2. Architecture & Stack
- **Data Extraction:** Prozorro Open Contracting API (`requests`)
- **Data Transformation:** `pandas` -> flattened tables stored in `duckdb` (tables: `tenders`, `items`).
- **Vector Storage:** `chromadb` using `sentence-transformers` (model: `multilingual-e5-large`).
- **LLM / RAG:** Local `ollama` (model: `llama3.1:8b`).

## 3. Current State (What is done)
We have successfully built and verified, end-to-end with live Ollama calls (`qwen2.5:14b-instruct`, **1047 tenders / 9273 items loaded**):
- `extract_prozorro.py`: Downloads JSON tenders (limit raised from 500 to 1000; dataset grew from 47 -> 1047 raw tenders).
- `transform_prozorro.py`: Flattens JSON into `prozorro.duckdb`.
- `load_chroma.py`: Chunks data, embeds, and loads into ChromaDB (correctly handling pd.NA).
- `rag_query.py` (V2, hybrid): A keyword router (`classify_query`) sends aggregate/ranking questions to a text-to-SQL path and everything else to the vector path.
  - **SQL path:** LLM writes a SELECT against the live DuckDB schema (fetched at runtime via `DESCRIBE`, not hardcoded) -> validated by `sqlglot` (single statement, must parse as SELECT/UNION, every table reference must resolve to a plain name in `{tenders, items}` — this also catches table-valued functions like `read_csv_auto(...)` whose Table node has no plain name, verified against `/etc/passwd`-style probes) -> executed read-only against DuckDB -> narrated by the LLM from the actual result rows.
  - **Vector path:** refuses to answer when nothing clears `RELEVANCE_THRESHOLD`, now **0.20** (re-calibrated for the 1047-tender dataset — see below).
  - Router is a curated keyword list (`QUANT_KEYWORDS`), not a classifier — deliberately narrow (e.g. "скільки тендерів" but not bare "скільки", since "скільки коштує X" is a lookup, not an aggregate). Expect to tune this list as real queries surface misroutes.
- `telegram_bot.py`: aiogram v3 interface. Loads the embedding model + Chroma collection once at startup, runs each query through `answer_query` via `asyncio.to_thread`, splits replies over Telegram's 4096-char limit. Token lives in `.env` (see `.env.example`), verified working end-to-end against live Telegram.

### Relevance threshold re-calibration (1047-tender dataset)
Probed 10 known-present categories (drones, generators, medical materials, uniforms, fire/rescue equipment, ...) against 8 known-absent ones (submarines, hosting services, wedding banquets, ...). Unlike the 43-tender sample, there's **no longer a clean separating gap**: genuine hits range up to ~0.198 within top_k=8, while a few absent-category queries land as low as ~0.177-0.182 through incidental text overlap (e.g. "космічний телескоп" nearest-matches an aircraft CPV description mentioning "космічні апарати"). Raised the threshold to 0.20, prioritizing recall (the original bug: real hits like the Mavic 3 Pro tenders were near the old 0.19 edge) over precision. Verified both directions: the drone query now returns all 8 genuine hits, and a hosting-services query — though it now clears the vector gate — is still correctly declined by the LLM's own grounded-refusal instruction, since none of the retrieved context is actually about hosting. That refusal instruction is now the load-bearing second line of defense against residual false positives; re-verify it still holds whenever this threshold changes again.

### V3: Anti-corruption investigator persona + CTE support (this session)
Both the vector-path `SYSTEM_PROMPT` and the SQL narrator's prompt in `narrate_sql_result()` now frame the LLM as an investigative-journalist persona: proactively compare prices within the retrieved context/result set, flag repeat suppliers as a possible competition concern, use the exact phrase "⚠️ Можлива аномалія / Ризик переплати" only when the actual numbers support it, stay concise/bulleted, and never open with "На підставі наданого контексту..." or "Based on the provided context...". `generate_sql()` gained a worked CTE example (`WITH avg_price AS (...) ... JOIN avg_price ap ON true`) for "compare against the average" questions, and the router picked up `найчастіше`, `хто`, `постачальник`, `конкуренція` so supplier/ranking questions route to SQL instead of vector search.

Verified live: a supplier-concentration query now correctly generates and executes a CTE, and flags a supplier with 24 wins vs. next-highest 19; a medical-materials price-comparison query flags two devices priced 37x and 22x the category average, both with real tender_ids and amounts, concise bullets, no robotic preamble.

Two structural bugs surfaced and got fixed **independently of the prompt changes** (same principle as the SQL validation gate — don't rely on the model doing the right thing):
- **`extract_sql()` was eating `WITH`.** It trimmed everything before the first `SELECT` to strip LLM chatter, which also deleted a leading `WITH cte_name AS (` — turning every valid CTE into a syntax error. This, not a missing keyword from the model, was almost certainly the real cause of the original CTE failure report. Fixed to cut at whichever of `WITH `/`SELECT` appears first.
- **`validate_sql()` rejected CTE aliases as unknown tables**, since `FROM avg_price` looks identical to `FROM some_random_table` to a bare table whitelist. Fixed by collecting `WITH`-clause aliases per-statement and allowing them alongside `tenders`/`items`. Re-verified the injection probes still block a CTE that shadows the `tenders` name to smuggle in `read_csv_auto(...)`.
- **DuckDB's `LIKE` is case-sensitive**, and the LLM can't reliably reproduce a column's exact capitalization (real data: `Медичні матеріали`; generated: `медичні матеріали`) — this silently returned zero rows indistinguishable from "no such data." `validate_sql()` now rewrites every `LIKE` to `ILIKE` in the AST after all safety checks pass, regardless of what case the model generates. This was very likely causing silent false-"no data" answers on earlier queries too, not just the one that surfaced it.

### V4: NULL filtering, SQL hidden from end users, richer narration (this session)
Fixed three issues from live testing:
- **NULL/empty group-by values.** `generate_sql()` now has an explicit rule + worked example requiring `<field> IS NOT NULL` whenever grouping/aggregating by a nullable text field (`supplier_name`, `buyer_name`) — previously a "Хто з постачальників найчастіше виграє..." query put a nonsensical `None` (75 wins, tenders with no recorded supplier) at the top of the ranking.
- **Raw SQL no longer reaches the end user.** `answer_sql_query()` now `print()`s the generated/executing SQL to the terminal only (`[SQL DEBUG] ...`), and `narrate_sql_result()` no longer appends `\n\nSQL:\n{sql}` to its return value — confirmed by inspecting `answer_query()`'s return value directly (no `SELECT`/`WITH` substring present). `telegram_bot.py` needed no changes since it just relays whatever `answer_query()` returns; its docstring comment referencing an "SQL/sources block" was corrected since that's no longer accurate.
- **Richer, causally-explained narration.** The SQL narrator prompt now requires naming specific suppliers/buyers/tender_ids (never "one supplier" / "деякі тендери") and explaining the *mechanism* of each flagged risk in one sentence (e.g. "10 wins may indicate a monopoly or a tender spec tailored to one supplier"), not just labeling it an anomaly.

**Known residual flakiness, found while verifying the above:** the exact-phrase-plus-emoji requirement for `⚠️ Можлива аномалія / Ризик переплати` is not 100% reliable even after two rounds of prompt reinforcement — across test runs the model correctly identified the anomaly and explained it every time, but sometimes dropped the ⚠️ character or the exact capitalization (e.g. produced "можлива аномалія / Ризик переплати" mid-sentence instead of the canonical marker). This looks like a genuine local-LLM limitation with exact-literal-token reproduction rather than a prompt-wording problem — further reinforcement had diminishing returns. A deterministic backstop (detect anomaly-flagging language and normalize/insert the canonical marker) was considered and deliberately not added, since a naive version risks producing awkward duplicated phrasing when the model's own wording is already fine; revisit only if consistent-formatting turns out to matter more than the (already-reliable) substantive content.

### V5: Wartime supplier masking, router qualitative override, complex-aggregate CTEs (this session)
Fixed three more issues from live testing:
- **"Оборонний постачальник" was being flagged as a monopoly.** This is Prozorro's own masking convention for defense-sensitive procurements — an official redaction covering dozens of different real suppliers, not one company. Confirmed against the data: it's literally the single most frequent `supplier_name` value in the whole dataset (38 occurrences, more than the real top supplier's 24). Fixed in three places: (1) `generate_sql()`'s NULL-filtering rule now also excludes `supplier_name NOT ILIKE '%оборонний постачальник%'` / `'%приховано%'` whenever a query is about supplier concentration; (2) the SQL narrator prompt has an explicit carve-out telling it never to call this value a monopoly, and to explain it's masked instead if it shows up; (3) the vector-path `SYSTEM_PROMPT` got the same carve-out for its own repeat-supplier detection, since it has the identical blind spot even though it wasn't named in the bug report — same class of issue as the Omsk hallucination, so it seemed worth closing in both paths rather than just the one that got tested.
- **Router keyword collision between "найчастіше" and qualitative questions.** "Які технічні вимоги ... найчастіше ставлять" was routing to SQL (0 rows — there's no numeric field for "requirements") purely because it contained a quant keyword. Added `QUALITATIVE_OVERRIDE_KEYWORDS` (`характеристики`, `вимоги`, `опис`, `технічні` — matched anywhere) that wins over any `QUANT_KEYWORDS` match. `який`/`які` were requested too, but implemented differently: as a **leading-word-only** check, not anywhere-substring. Reason: your own Issue 3 test query contains "...замовника, **який** витратив найбільшу суму..." — there "який" is a relative pronoun mid-sentence, not the interrogative opening a qualitative question, and an anywhere-substring match would have force-routed that query to vector search, silently reintroducing the exact bug Issue 3 asked to fix in the same turn. Verified both directions land correctly (see test table below) — this is a case where following the literal instruction would have broken a different part of the same request, so it's implemented as a scoped-narrower version instead.
- **SQL crash on combined "average + top single record" queries.** The model was trying to cram an aggregate and a `MAX`-style lookup into one ungrammatical SELECT. `generate_sql()` gained a worked example: two independent CTEs (one scalar aggregate, one `ORDER BY ... LIMIT 1`) combined in the final SELECT via a scalar subquery for the aggregate and a plain `FROM` on the single-row CTE — no join needed since both sides are already exactly one row. Also made SQL execution failures print the actual exception (`[SQL DEBUG] Execution failed (<type>: <message>)`) to the terminal, matching the pattern already used for validation-gate rejections, so a future crash is debuggable without re-deriving what failed.

Router test table (`classify_query`), all confirmed correct: the two collision cases above, plus regression checks on "Хто з постачальників..." (sql), "скільки тендерів..." (sql), "дрони для розвідки" (vector), and a synthetic "який опис має ця закупівля?" (vector, leading-word case).

### V10: Investigation templates — Skill/Template architecture for corruption schemes (this session)
New module `investigations.py`, deliberately kept dependency-free of `rag_query.py` (one-directional import: `rag_query.py` imports from `investigations.py`, never the reverse) — see its module docstring for the full reasoning. Three hardcoded, code-reviewed SQL templates replace free-form generation for the query shapes an 8B/14B local model is least reliable at:
- **Tender splitting** (`дроблен`/`схем` triggers): flags 3+ contracts of 90,000-99,999 UAH from the same buyer to the same supplier — the classic just-under-the-competitive-bidding-threshold evasion pattern. Optional buyer filter; runs market-wide otherwise.
- **Local monopoly / favoritism** (`улюблен`/`монопол` triggers): top suppliers by win count and total amount for one named buyer.
- **Apples-to-apples overpricing** (`найбільше переплатив`/`переплатив за` triggers): the max `unit_amount` for one *exact* item pattern vs. AVG/MEDIAN/`sample_size` computed over that same exact pattern — structurally cannot fall back to a broader category the way the free-form CTE path (V9) still technically could.

**Why templates instead of more prompt engineering on `generate_sql()`:** the LLM's only job is extracting a parameter (buyer name, item model) — bound as a real DuckDB `?` parameter, never string-interpolated. Verified live with an actual `'; DROP TABLE tenders; --` value bound as a parameter: completely inert, zero rows, table untouched. This gives these three query types zero injection surface independent of `validate_sql`'s AST gate, and bakes the "Оборонний постачальник" masking exclusion (V5) into the WHERE clause as literal Python — not something an LLM has to remember every time.

### V12: Production deployment — incremental ETL, LLM provider abstraction, Docker, scheduling (this session)
Four architectural additions for moving off a local always-on MVP:

- **Incremental updates (`update_data.py`, new module).** Resume point is `MAX(date_modified)` already in DuckDB (verified live: passing that exact timestamp as the API's `offset` returns only tenders modified strictly after it). Refactored `transform_prozorro.py` to split out `finalize_dataframes()` (dtype cleanup, dedup-keep-latest, `price_deviation_pct` recompute) from `build_dataframes()`, so the incremental path reuses the *exact* same logic on `pd.concat([existing, new])` rather than re-deriving it — the existing dedup-by-`tender_id`-keep-latest-`date_modified` step was already written for exactly this "same tender re-fetched across sync runs" case. Refactored `load_chroma.py` similarly (`embed_and_upsert()` extracted from `run_load()`) so only the touched tenders get re-embedded, not the whole collection — `collection.upsert()` is already idempotent by ID. `extract_prozorro.run_extraction()` gained an `overwrite` param: the historical backfill still skips a tender_id it already has cached, but incremental sync always re-fetches, since being in the sync window at all means new-or-updated.
  - **Real bug found and fixed while running this live, not in a test:** an unattended incremental run crashed entirely on a plain `requests.exceptions.ReadTimeout` — `run_extraction`'s except clause only caught `requests.HTTPError` (4xx/5xx responses), not the separate `RequestException` hierarchy that covers timeouts/connection errors. For a 24/7 unattended job this is a real reliability gap, not a cosmetic one: one transient network blip would silently kill the whole nightly sync. Added `_get_with_retry()` (one retry after a short backoff on any `RequestException`) used by both the list-endpoint walk and the per-tender detail fetch, widened the per-tender except clause to `RequestException`, and wrapped the outer walk loop too so a persistent list-endpoint outage returns partial progress instead of raising and losing everything collected so far. Verified: re-ran the exact same incremental sync after the fix; see below for the full-run result.
- **LLM provider abstraction (`llm_client.py`, new module).** `LLM_PROVIDER=ollama|openai` in `.env`; every `ollama.chat(...)` call site in `rag_query.py` and `investigations.py` (4 and 2 respectively) now goes through `llm_client.chat()`/`llm_client.health_check()` instead. Used the plain `openai` package rather than LangChain — reasoning is in the module docstring (single request/response per call site, no chains/agents/LLM-orchestrated retrieval to justify the extra dependency and abstraction layer). Verified both providers for real: the `ollama` path end-to-end via `rag_query.py` CLI (no regression from the refactor), and the `openai` path two ways — confirmed `health_check()` correctly rejects a missing `OPENAI_API_KEY`, then confirmed a deliberately fake key reaches the real OpenAI API and gets a clean `401 AuthenticationError` back (proving the request is genuinely well-formed, not just plausible-looking — a malformed request would fail differently, e.g. a client-side `TypeError` or a `400`). Also discovered (and documented in `.env.example`) that the `ollama` package already reads `OLLAMA_HOST` from the environment natively — no project code needed for the "point at a remote/GPU-hosted Ollama" case.
- **Dockerization.** `Dockerfile` (python:3.13-slim, no Ollama bundled — see below) and `docker-compose.yml` supporting two modes: a cheap VPS running `LLM_PROVIDER=openai` (default `docker compose up -d`, the `ollama` service never starts), or a GPU host running Ollama either as a sibling container (`--profile local-llm`) or on a separate machine (`OLLAMA_HOST` pointed at it). `data/` and `chroma_db/` are bind-mounted, not left in the container's writable layer. **Actually built the image twice, not just written**: first build succeeded end-to-end (~11 min, mostly torch/CUDA wheel downloads); after adding `apscheduler` to `requirements.txt`, rebuilt and confirmed with `docker run` that every project module (`llm_client`, `update_data`, `extract_prozorro`, `transform_prozorro`, `load_chroma`, `investigations`, `rag_query`, `telegram_bot`) actually imports inside the running container, not just that the Dockerfile looks plausible.
- **Nightly automation.** `telegram_bot.py` starts an `AsyncIOScheduler` (runs on the bot's own asyncio event loop, not a separate OS thread — simpler and consistent with this file's existing `asyncio.to_thread` pattern for keeping the loop responsive) that fires `update_data.run_update()` daily at `UPDATE_SCHEDULE_HOUR:MINUTE` (`.env`, default 3:00 AM) via `asyncio.to_thread`, with exceptions caught and logged in the job wrapper (an uncaught exception in an APScheduler job is otherwise silently swallowed by the scheduler — logging it is the only way to notice a failed nightly run). Verified the cron trigger registers correctly and computes the right next-run time. `DEPLOY.md` documents an equivalent system-crontab alternative for anyone who'd rather the update run as a fully separate process — explicitly warns not to run both mechanisms against the same DuckDB file at once, since the merge step isn't designed for concurrent writers.

**Post-session verification found two more real issues — both only visible by actually running things, not by building/writing them:**
- **The V12 network-resilience fix earned its keep on the very next real run.** A full, unattended `update_data.py` catch-up run (2000-tender cap, ~50 min) hit 11 genuine `Connection reset by peer` errors from the Prozorro API mid-run — every one caught by `_get_with_retry()`, retried once, and recovered; zero skipped tenders, zero aborted walks, the run completed cleanly at 2000/2000. Before today's fix, any one of those 11 would have crashed the entire nightly sync unattended. Dataset grew from 6050 to 7555 tenders / 42019 items this way, catching up to `date_modified` through 2026-08-25 09:01 (the real backlog exceeded the 2000 cap, so it didn't reach all the way to "now" in one run — expected, the scheduler picks up the rest on subsequent nights).
- **`docker compose up` crashed on the very first real run** — this is exactly why "the image builds" and "the app works" are different claims. Inside a fresh container (no pre-existing pip cache, so every dependency resolved to whatever was newest at build time), loading `intfloat/multilingual-e5-large` failed with `ValueError: Unrecognized processing class` from `AutoProcessor.from_pretrained` — a real behavioral regression in `transformers==5.16.1` vs the `5.15.1` already proven working in the local venv (same `sentence-transformers==6.0.0` either way; the transitive `transformers` version is what silently drifted). Root cause: `requirements.txt` had no version pins at all, so a from-scratch container build was never guaranteed to reproduce the locally-tested environment — it happened to work the first two times this session only because the pip resolver picked compatible versions by chance. **Fixed by pinning every dependency in `requirements.txt` to its exact locally-verified version** (via `pip freeze`), not just `transformers` — the whole point of a lockfile-style pin is that the *next* silent minor-version drift shouldn't get a free pass either. Rebuilt and re-verified the container actually reaches `Run polling for bot...` after the pin.
- **The scheduled 03:00 job silently never fired, for ~16 hours straight, with zero log trace.** Found by actually checking: the container ran continuously (confirmed via `docker inspect` — 0 restarts) from 2026-08-26 23:37 through the next day, but grepping the full log for the scheduled job's own "Starting scheduled..." line, or even APScheduler's own default misfire WARNING ("Run time of job ... was missed by ..."), found nothing at all. Reproduced the exact mechanism deliberately: `AsyncIOScheduler`'s default `misfire_grace_time` is **1 second** (confirmed via `scheduler._job_defaults`) — a genuine event-loop stall/pause (a Docker Desktop host sleep on macOS is the leading suspect here, though a real always-on Linux server is far less exposed to this specific trigger) past that 1-second window causes APScheduler to drop the run entirely, and a deliberately-forced version of this exact scenario (blocking the loop past the fire time) confirmed the drop happens **with no log output at all** unless the miss is caught by the loop before the grace window fully elapses. This is a materially different — and worse — failure mode than "logs a warning and skips," which is what the original design assumed. Fixed two ways, since a wider grace period alone doesn't fully close the gap (it only shrinks the window, doesn't guarantee catching an arbitrarily long pause): (1) `misfire_grace_time=3600` (an hour) makes small stalls survive; (2) a genuine backstop — `update_data.hours_since_last_sync()` (new) checks data freshness at bot startup, and if it exceeds `UPDATE_STALE_THRESHOLD_HOURS` (`.env`, default 30h), fires an immediate catch-up via `asyncio.create_task(scheduled_update_job())` rather than waiting for the next scheduled tick. Also added an `EVENT_JOB_MISSED` listener (`_on_job_missed`) so if a miss *does* still happen, it's now impossible to miss in the logs. **Verified live, not just built**: rebuilt and restarted the container with real 55.2h-stale data — startup log shows `WARNING Data is 55.2h stale (> 30.0h threshold) ... Running a catch-up update now`, immediately followed by `Bot starting polling...` on the very next line, confirming the fire-and-forget `asyncio.create_task` correctly lets the catch-up run concurrently with the bot answering messages, exactly as designed — not blocking startup.
- Also observed live in this same container: `TelegramNetworkError` (request timeouts / server-disconnects) roughly every 15-45 minutes, each one recovered automatically by aiogram's own built-in backoff-and-retry (confirmed via source: `await backoff.asleep()`, not a blocking sleep, so this doesn't stall the event loop or explain the scheduler miss above). Not a bug, just noisy — worth knowing this is normal background chatter in the container's logs, not a sign of instability.

## 4. Known follow-ups / open issues
- V12's incremental merge has no `PRIMARY KEY`/true SQL `UPSERT` — it works (correctly, verified) by reading the whole `tenders`/`items` tables into pandas, concatenating with the freshly flattened rows, and rewriting via `CREATE OR REPLACE`. Fine at thousands of rows; would need revisiting (a real primary key + `ON CONFLICT DO UPDATE`, or partitioned storage) if the dataset ever grew into the high hundreds-of-thousands or millions.
- `update_data.py`'s `MAX_TENDERS_PER_RUN = 2000` safety cap means a sync that's been down for a long time won't fully catch up in one run — it'll just pick up more next time the schedule fires, but a very long outage needs a human to notice and possibly re-run manually a few times.
- The built-in `AsyncIOScheduler` and the `DEPLOY.md` crontab alternative are meant to be mutually exclusive, but nothing in the code enforces that — running both against the same `data/prozorro.duckdb` would be two concurrent writers, and the merge step isn't designed for that. Documented as a warning in `DEPLOY.md`, not structurally prevented (e.g. no file lock).
- The Docker image runs as root inside the container — a deliberate simplification given no exposed network ports and a single-operator deployment model, not an oversight, but worth revisiting if this ever becomes multi-tenant or network-facing.
- Same recurring test-suite gap, now with more surface area: `llm_client`'s provider switching, `update_data.py`'s merge/dedup logic, and `extract_prozorro.py`'s retry behavior would all benefit from pinned regression tests, same as the SQL validation gate and router heuristics noted elsewhere in this file.
- ~~English `LIKE` patterns against Ukrainian text columns~~ — fixed. The text-to-SQL system prompt in `generate_sql()` now states the DB is Ukrainian-language, forbids English literals in LIKE/`=` on text columns, and prefers `cpv_main`/`items.cpv` prefix filtering (CPV is language-neutral) over text matching.
- ~~Fan-out double-counting~~ — fixed. While verifying the language fix, found the LLM was joining `tenders` to `items` for tender-level aggregates (`SUM(awarded_amount)` etc.), which double-counts a tender once per item row — a real query was overstated 10x (202.6M vs correct 19.7M) before the fix, and a second variant (filtering on `items.cpv` while aggregating a tenders column) still fanned out afterward until the prompt was also taught to use `IN (SELECT tender_id FROM items WHERE ...)` instead of a JOIN for that case. Both now verified correct against direct DuckDB queries. This class of bug is prompt-compliance-dependent, not structurally prevented — worth periodic spot-checks against manual queries as the model or dataset changes.
- ~~Narration-layer hallucination~~ — fixed. Live Telegram testing surfaced qwen2.5:14b-instruct misreading the buyer-name abbreviation "ОМР" (Одеська міська рада) in a retrieved chunk as the Russian city Omsk, and independently fabricating three plausible-looking tender URLs (`public.prozorro.sale.ua` isn't even a real domain — no URL field exists anywhere in the pipeline). Fixed in two layers, matching the SQL validation-gate philosophy of not trusting prompt compliance alone: (1) `SYSTEM_PROMPT` now explicitly forbids reinterpreting proper-noun abbreviations and forbids generating any link; (2) `strip_fabricated_links()` deterministically strips markdown links and bare URLs from every LLM answer (vector path and SQL narration both) regardless of whether the model obeyed. Re-verified with a targeted "хто замовник тендеру UA-2023-12-13-014703-a" query — now correctly returns "Департамент муніципальної безпеки ОМР (Одеська область)" with no Omsk/Russia misattribution and no links.
- No test suite yet — `validate_sql` deserves unit tests pinning the blocked/allowed cases (DDL, stacked statements, unknown tables, table-valued functions, CTE aliases, CTE-shadowing an allowed table name), the fan-out fix deserves a regression test (an aggregate query with a CPV filter, asserting the result matches a query without the corresponding JOIN), and `strip_fabricated_links` and the `LIKE`->`ILIKE` rewrite each deserve one too, so none of these gaps can silently reopen.
- The anti-corruption anomaly flag is prompt-driven pattern-matching over whatever the SQL/vector result happens to contain — it has no concept of statistical significance or false-positive rate beyond the sample-size floor added in V9. Treat its flags as investigative leads to check, not verified findings. Note: as of V4 the underlying SQL is intentionally no longer shown to end users (see below) — if you need to audit a flagged answer, rerun the same query from a terminal (`python rag_query.py --query "..."`) and read the `[SQL DEBUG]` line, or check the `telegram_bot.py` process's own terminal output.
  - ~~Blended category average overstating anomalies (e.g. "37x the average" from cheap consumables mixed with expensive equipment)~~ — addressed in V9 by narrowing the comparison group to similar items instead of the whole category, with a `sample_size` floor as a deterministic backstop.

(2) When a user's own query doesn't name a specific item/model (e.g. a broad "чи є аномалії серед дронів?" with no model named), there's nothing concrete to narrow the comparison average to, so the SQL may still legitimately fall back to a broader category — worth watching whether the model at least flags that broader-comparison caveat itself in that case, since the `sample_size` backstop won't catch a broad-but-not-too-small sample.
